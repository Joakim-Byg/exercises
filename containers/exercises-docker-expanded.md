# Chapter 1: Container Management with Docker

Containers package software and its dependencies into a single, predictable unit that runs consistently across different computing environments. This chapter covers the fundamental concepts and command-line tools needed to run, inspect, and manage containers on a local system using Docker.

## Learning objectives

After this chapter you can:
- List and interpret the lifecycle states of local containers.
- Pull container images from registries and run them interactively or in the background.
- Expose containerized services to a host network using port mapping.
- Mount host directories as volumes for application configuration and log persistence.
- Build secure, custom container images using Dockerfiles and non-root users.

## Before you start

To complete this chapter, you must have Docker installed and running on your local machine or workstation. You should be familiar with using a Unix-like shell, running standard commands, and navigating directories. All command blocks in this chapter assume a local bash or zsh shell on a machine with Docker running.

## Verifying the Docker Environment

Before starting to run applications, you should check that the container daemon is active and accessible.

To do this, use `docker info` to print the system configuration, followed by `docker version` to verify that the client and server components are communicating.

```bash
docker info
docker version
```

### Explaining the diagnostic commands

- **`docker info`** (**docker** **info**rmation)
  - **What it does:** Displays system-wide configuration, including the active storage driver, the number of running/paused containers, and system resources.
  - **Memory hook:** Think of this as the dashboard or diagnostic report for your container engine.

- **`docker version`** (**docker** **version**)
  - **What it does:** Displays the version numbers for both the client (your command-line interface) and the daemon (the background server process).
  - **Memory hook:** Use this to verify that the CLI tool can actually talk to the background service.

### Running a test container

With the daemon verified, run a minimal test image to confirm that Docker can retrieve and run containers:

```bash
docker run hello-world
```

- **`docker run`** (**docker** **run**)
  - **What it does:** Downloads an image (if not present locally), creates a container from it, and starts it.
  - **Memory hook:** This command is the primary entry point to launch an application inside a container.

When you run this command, the engine looks for an image named `hello-world` locally. If it cannot find it, it fetches it from the default public registry, extracts the filesystem layers, instantiates the container, and runs its default program. This particular container displays an informational message and then exits immediately.

## Managing Containers and Their Lifecycle

Containers are active processes running on top of the host kernel, isolated by Linux namespaces and control groups. Managing them requires checking their status, viewing their output, and cleaning up stopped instances.

### Running a Background Web Server

Most server applications should run in the background rather than blocking your terminal. Use the Nginx web server to practice this:

```bash
docker run -d --name my-nginx nginx
```

The `-d` flag runs the container in detached mode (in the background), printing only the long container ID. The `--name` flag assigns a friendly alias, `my-nginx`, so you can manage the container without typing the ID.

### Checking Process Status

To see active containers, use `docker ps`:

```bash
docker ps
```

- **`docker ps`** (**docker** **p**rocess **s**tatus)
  - **What it does:** Lists currently running containers.
  - **Memory hook:** This is the container equivalent of the standard Linux `ps` command.

The output displays columns for the container ID, image name, the command being run, creation time, status (such as `Up 2 minutes`), forwarded ports, and the friendly name.

### Reading Container Output and Metadata

Since detached containers run in the background, you cannot see their console output directly. Use `docker logs` to retrieve their stdout and stderr streams:

```bash
docker logs my-nginx
```

- **`docker logs`** (**docker** **logs**)
  - **What it does:** Displays the console output (stdout and stderr) generated by a container.
  - **Memory hook:** Use this as your primary troubleshooting step when a background container stops unexpectedly or acts up.

For low-level configuration details, use `docker inspect`:

```bash
docker inspect my-nginx
```

- **`docker inspect`** (**docker** **inspect**)
  - **What it does:** Returns a detailed JSON array describing the container's configuration, environment, networking, and state.
  - **Memory hook:** Think of this as an X-ray scan showing exactly how the engine configured the container's virtual hardware and software variables.

### Stopping and Cleaning Up Containers

When a container is no longer needed, you can stop its execution and remove its filesystem.

```bash
docker stop my-nginx
```

- **`docker stop`** (**docker** **stop**)
  - **What it does:** Gracefully stops a running container by sending a `SIGTERM` signal, followed by a `SIGKILL` if it fails to stop within a grace period.
  - **Memory hook:** This is like shutting down a server using its power button rather than pulling the plug.

Once stopped, the container is no longer active, but its filesystem and configuration remain on disk. To list stopped containers, add the `-a` (all) flag:

```bash
docker ps -a
```

To free up storage and system resources, delete the container:

```bash
docker rm my-nginx
```

- **`docker rm`** (**docker** **r**e**m**ove)
  - **What it does:** Permanently deletes a stopped container, destroying its read-write filesystem layer.
  - **Memory hook:** This deletes the specific instance of the container while keeping the original image intact.

### Batch Cleanup of Extracted Containers

Every time you run `docker run hello-world`, a new stopped container remains on disk. To clean up multiple exited containers, filter by the parent image and pass their IDs to `docker rm`:

```bash
docker ps -a -f "ancestor=hello-world"
docker rm $(docker ps -a -q -f "ancestor=hello-world")
```

The `-q` (quiet) flag restricts the output to container IDs, allowing command substitution to pass them directly to `docker rm`.

> [!WARNING]
> **Common pitfalls**
>
> - **Attempting to remove a running container** — Running `docker rm my-nginx` on an active container fails. You must run `docker stop my-nginx` first, or force removal with `docker rm -f my-nginx`.
> - **Confusing container removal with image removal** — Running `docker rm` deletes the execution instance. It does not delete the template image from your disk.

## Managing Local Images

Images are read-only templates composed of layered filesystems. They form the static blueprint from which containers are built.

### Inspecting Local Images

To list all images stored locally on your host:

```bash
docker images
```

- **`docker images`** (**docker** **images**)
  - **What it does:** Lists all images downloaded or built on your local host, showing their repository names, tags, and sizes.
  - **Memory hook:** Think of this as your local storage library of template filesystems.

### Downloading New Images

To fetch an image from a container registry without running it immediately:

```bash
docker pull ubuntu:latest
```

- **`docker pull`** (**docker** **pull**)
  - **What it does:** Downloads an image and its layered components from a remote registry to your local machine.
  - **Memory hook:** This retrieves the static files so you can build containers from them later.

### Running Interactive Environments

You can instantiate an image and open an interactive shell inside it to explore its environment:

```bash
docker run -it ubuntu:latest bash
```

The `-i` (interactive) flag keeps standard input open, and `-t` allocates a pseudo-TTY (terminal). This connects your current terminal directly to the container's `/bin/bash` process. Inside, you can run normal commands like `ls /` or `apt update`. Typing `exit` stops the bash process, which also stops the container.

### Deleting Images

To free up disk space, delete images that you no longer need:

```bash
docker rmi ubuntu:latest
```

- **`docker rmi`** (**docker** **r**e**m**ove **i**mage)
  - **What it does:** Deletes a locally stored image if no existing containers (running or stopped) depend on it.
  - **Memory hook:** The extra `i` stands for "image", distinguishing this command from the container-removal command `docker rm`.

## Interacting with Running Containers

You can run new processes inside a container that is already running in the background. This is useful for inspection, debugging, or administration.

### Running Commands in Background Containers

Start Nginx again in the background:

```bash
docker run -d --name my-nginx nginx
```

Instead of starting a new container to run a shell command, execute the command directly inside the active `my-nginx` container:

```bash
docker exec my-nginx getent passwd | awk -F: '{ print $1}'
```

- **`docker exec`** (**docker** **exec**ute)
  - **What it does:** Spawns a new process inside an already-running container.
  - **Memory hook:** Use this to run diagnostic commands or open a shell inside an active container without restarting it.

This command runs `getent passwd` inside the container, extracts the usernames, and prints them to your host terminal.

### Opening an Interactive Shell in an Active Container

To inspect the filesystem of a running container, start an interactive bash session:

```bash
docker exec -it my-nginx bash
```

This attaches a terminal to a new bash process inside the running Nginx container. You can run `curl localhost` to query the web server locally from within its own network namespace. Type `exit` to close the shell; the container and Nginx will continue running undisturbed in the background.

To clean up:

```bash
docker stop my-nginx
docker rm my-nginx
```

## Exposing Services with Port Mapping

By default, containers reside on isolated, private bridge networks. Services listening inside a container are inaccessible from the host machine or external network unless you explicitly publish their ports.

### Mapping Container Ports to Host Ports

Start Nginx and map its standard HTTP port (80) to port 8080 on your host machine:

```bash
docker run -d --name my-web-server -p 8080:80 nginx
```

The `-p 8080:80` flag instructs the engine to listen on host port 8080 and forward all incoming TCP traffic to port 80 inside the container.

### Verifying Network Reachability

You can verify the connection by navigating to `http://localhost:8080` in a web browser, or by using curl in your terminal:

```bash
curl http://localhost:8080
```

When you inspect the process status with `docker ps`, you will see the active forwarding rule listed under the `PORTS` column as `0.0.0.0:8080->80/tcp`.

To clean up:

```bash
docker stop my-web-server
docker rm my-web-server
```

## Persisting Data with Volume Mounts

Containers are designed to be ephemeral and stateless. When a container is deleted, any files written to its read-write layer are lost forever. To persist data or share configuration files between the host and the container, use volume mounts.

### Mounting Host Directories for Content Delivery

Create a directory on your host and write an HTML file to it:

```bash
mkdir ~/nginx-html
echo "<h1>Hello from Docker Volume</h1>" > ~/nginx-html/index.html
```

Now, launch Nginx and mount this directory over its default web root directory:

```bash
docker run -d --name volume-nginx -p 8081:80 -v ~/nginx-html:/usr/share/nginx/html nginx
```

The `-v ~/nginx-html:/usr/share/nginx/html` flag maps the host directory `~/nginx-html` directly to the container's web directory `/usr/share/nginx/html`. Any files in that host directory override the container's default files.

Query the web server to verify it serves your custom file:

```bash
curl http://localhost:8081
```

If you modify the file on your host machine, the web server reflects the change immediately because both the host and container access the same physical files:

```bash
echo "<h1>Updated Content</h1>" > ~/nginx-html/index.html
curl http://localhost:8081
```

### Providing Configuration Files

You can also mount individual files to configure applications. Create a custom configuration file for Nginx:

```bash
mkdir ~/nginx-conf
echo "server { listen 80; location / { return 200 'Hello from Custom Config'; } }" > ~/nginx-conf/custom.conf
```

Run Nginx, mounting this file over its default configuration path:

```bash
docker run -d --name custom-conf-nginx -p 8082:80 -v ~/nginx-conf/custom.conf:/etc/nginx/conf.d/default.conf nginx
```

Test the endpoint:

```bash
curl http://localhost:8082
```

Because Nginx reads its configuration file once during startup, modifying the host file will not update the running server's behavior immediately:

```bash
echo "server { listen 80; location / { return 200 'Config updated\n'; } }" > ~/nginx-conf/custom.conf
curl http://localhost:8082
```

To apply the new configuration, restart the container process:

```bash
docker restart custom-conf-nginx
curl http://localhost:8082
```

To clean up:

```bash
docker stop volume-nginx custom-conf-nginx
docker rm volume-nginx custom-conf-nginx
rm -rf ~/nginx-html ~/nginx-conf
```

### Extracting Application Logs

Volumes can also capture logs written by containerized applications, keeping them accessible on the host even after the container is destroyed.

Create a host directory for the logs:

```bash
mkdir -p ~/app-logs
```

Start an Alpine Linux container that writes to a log file, mounting your host directory:

```bash
docker run -d --name log-generator -v ~/app-logs:/app/logs alpine \
    sh -c 'while true; do echo "[$(date +"%F %H:%M:%S")] Log entry from container" >> /app/logs/app.log; sleep 1; done'
```

Monitor the log file from your host machine:

```bash
tail -f ~/app-logs/app.log
```

Even if you stop and delete the container, the logs remain safe on your host disk:

```bash
docker stop log-generator
docker rm log-generator
cat ~/app-logs/app.log
rm -rf ~/app-logs
```

## Building Custom Images

To run custom applications, you must build your own container images using a recipe file called a `Dockerfile`.

### Writing a Basic Dockerfile

Create a directory for your application build context:

```bash
mkdir my-app && cd my-app
echo "<h1>My Custom Web App</h1>" > index.html
```

Create a file named `Dockerfile` and add the following instructions:

```dockerfile
# Use an official Nginx image as the base
FROM nginx:latest

# Copy your custom index.html into the Nginx web root
COPY index.html /usr/share/nginx/html/index.html

# Expose port 80 (optional, but good practice for documentation)
EXPOSE 80

# Command to run when the container starts
CMD ["nginx", "-g", "daemon off;"]
```

Build the container image:

```bash
docker build -t my-custom-nginx .
```

- **`docker build`** (**docker** **build**)
  - **What it does:** Builds a new container image using the instructions defined in a local `Dockerfile` and a build context.
  - **Memory hook:** This acts like a compiler, transforming a text-based instruction sheet into a static executable image.

The `.` argument represents the current directory, which serves as the build context. The tag `-t` names the resulting image `my-custom-nginx`.

To verify and run your new image:

```bash
docker images
docker run -d --name custom-web -p 8083:80 my-custom-nginx
curl http://localhost:8083
```

To inspect how the image layers were assembled:

```bash
docker history my-custom-nginx
```

- **`docker history`** (**docker** **history**)
  - **What it does:** Displays the filesystem layers, size, and instructions used to construct each layer of an image.
  - **Memory hook:** Think of this as a git commit history showing each change made during the image's creation.

### Distributing Images to Container Registries

Container registries let you publish and share images with other hosts and users.

Before pushing an image, you must authenticate to the registry and apply a tag that matches the destination repository namespace:

```bash
# 1. Authenticate (using Azure as an example registry)
az login --identity
az acr login --name myregistry.azurecr.io

# 2. Tag the image with the registry address and path
docker tag my-custom-nginx:latest myregistry.azurecr.io/myusername/my-custom-nginx:latest
```

- **`docker tag`** (**docker** **tag**)
  - **What it does:** Creates an alias pointing to an existing source image.
  - **Memory hook:** Think of this as creating a symlink or shortcut pointing to a file under a new name or namespace.

Now, push the image to the remote registry:

```bash
docker push myregistry.azurecr.io/myusername/my-custom-nginx:latest
```

- **`docker push`** (**docker** **push**)
  - **What it does:** Uploads a local image and its distinct layers to a container registry.
  - **Memory hook:** This publishes your local template so that other systems can pull and run it.

To test that the upload succeeded, delete your local copy and pull it back down:

```bash
docker rmi myregistry.azurecr.io/myusername/my-custom-nginx:latest
docker pull myregistry.azurecr.io/myusername/my-custom-nginx:latest
docker run -d --name registry-nginx -p 8083:80 myregistry.azurecr.io/myusername/my-custom-nginx:latest
```

To clean up:

```bash
docker stop custom-web registry-nginx
docker rm custom-web registry-nginx
docker rmi my-custom-nginx myregistry.azurecr.io/myusername/my-custom-nginx:latest
cd ..
rm -rf my-app
```

### Enhancing Security: Running as a Non-Privileged User

By default, many containers run their applications as the root user. If an attacker exploits a vulnerability in your application, they can gain root access inside the container and potentially exploit host systems. Security standards require running processes as non-root users whenever possible.

Create a new secure build directory:

```bash
mkdir my-app-secure && cd my-app-secure
echo "<h1>Secure Web App</h1>" > index.html
```

Create a `Dockerfile` that sets up a dedicated, non-privileged user:

```dockerfile
# Use a minimal, secure base image
FROM alpine:latest

# Create a non-root group and user
RUN addgroup -S appgroup && adduser -u 1500 -S appuser -G appgroup

# Copy your application files
COPY index.html /var/www/html/index.html

# Install Python and assign ownership of the web root to your user
RUN apk add --no-cache python3 && chown -R appuser:appgroup /var/www/html

# Switch to the non-privileged user
USER appuser
WORKDIR /var/www/html

# Expose an unprivileged port (ports below 1024 require root privileges)
EXPOSE 8080

# Run a simple Python web server
CMD ["python3", "-m", "http.server", "8080"]
```

Build and run your secure container:

```bash
docker build -t my-secure-app .
docker run -d --name secure-web -p 8084:8080 my-secure-app
```

Verify that the process runs as your non-root user instead of root:

```bash
docker exec secure-web id
```

You should see an output indicating the active user ID (`uid=1500(appuser)`).

To clean up:

```bash
docker stop secure-web
docker rm secure-web
docker rmi my-secure-app
cd ..
rm -rf my-app-secure
```

## Multi-Container Orchestration with Compose

Docker Compose lets you define and manage multi-container applications in a single configuration file.

### Defining a Compose File

Create a directory for your project:

```bash
mkdir my-compose-app && cd my-compose-app
```

Create a file named `docker-compose.yml` to define your web service:

```yaml
version: '3.8'

services:
  web:
    image: nginx:latest
    ports:
      - "8083:80"
    volumes:
      - ./html:/usr/share/nginx/html
```

Create the mounted HTML directory and index file:

```bash
mkdir html
echo "<h1>Hello from Docker Compose</h1>" > html/index.html
```

### Operating Compose Applications

To orchestrate and launch your stack, run `docker compose up`:

```bash
docker compose up -d
```

- **`docker compose`** (**docker** **compose**)
  - **What it does:** Orchestrates and manages multi-container environments defined in YAML configuration files.
  - **Memory hook:** Think of this as a conductor directing an orchestra of distinct container services.

The `-d` flag runs the services in the background. The command automatically creates the network and launches the Nginx container, mounting the host's `./html` directory.

Verify reachability:

```bash
curl http://localhost:8083
```

To stop and completely tear down the services, networks, and containers created by your configuration:

```bash
docker compose down
```

The `down` command stops the active processes and removes the containers and network setup, leaving your host system clean.

To clean up:

```bash
cd ..
rm -rf my-compose-app
```
